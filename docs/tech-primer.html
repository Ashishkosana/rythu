Rythu — Technical Primer

Every concept you should understand before writing code — plain English + why it matters for this app. Curated to industry best-practice. Don't memorize; understand the mechanism.

Stack we're targeting: React + TypeScript (Next.js) frontend · Python serverless backend on AWS · rule-based advisory engine.

1 · Architecture & how the pieces talk

Client–Server
The phone app (client) asks a server for data over the internet. Rythu's app is the client; our AWS backend is the server.
REST API / endpoint
A defined URL the app calls to get/send data (e.g. GET /weather?district=bhupalpally). Each such URL = an "endpoint". The contract between frontend & backend.
JSON
The text format APIs speak. {"tempC":29,"rain":false}. Both React and Python parse it natively.
Hexagonal / Ports & Adapters
Backend design where your core logic doesn't know about DBs or external APIs — it talks to "ports" (interfaces), and "adapters" plug in the real thing. Lets you swap OpenWeather→IMD without touching logic. (Your backend already uses this.)
Monorepo
One repo holding web/ + backend/ + infra/. Simpler for a 2-person team than juggling repos.

2 · Frontend (React + TypeScript)

React
A library for building UIs out of reusable components (a WeatherCard, a CropCard). You describe what the UI should look like for given data; React updates the screen.
Component
A self-contained piece of UI (function returning markup). You compose small ones into screens.
Props & State
Props = data passed into a component. State = data that changes over time (e.g. selected crop) and re-renders the UI when it changes.
Hooks (useState, useEffect)
Functions that add state/side-effects to components. useEffect runs code on load (e.g. fetch weather).
TypeScript
JavaScript + types. Catches bugs before runtime (e.g. "temp is a number, not a string"). Industry standard; also what closes your React gap.
Next.js
A React framework: routing, server-rendering, easy deploy. Gives structure so you don't wire everything by hand.
Tailwind CSS + shadcn/ui
Utility CSS + ready-made accessible components. How you get a polished UI/UX without being a designer (this prototype uses Tailwind).
TanStack Query
Handles fetching/caching API data (loading states, refetch, stale data). Don't hand-roll this.
Responsive / mobile-first
UI that works on a small cheap phone first. Farmers aren't on desktops.
i18n / localization
Building the app so all text can switch language. Telugu strings live in files, not hard-coded — critical for this app.
PWA / offline-first
A web app that installs like a native app + works with poor/no connectivity by caching. Big deal for rural users.

3 · Backend & cloud (AWS serverless)

Serverless / AWS Lambda
Your code runs on-demand without you managing servers; you pay per request. Cheap for a pilot.
API Gateway
The front door that receives the app's HTTP calls and routes them to your Lambdas.
DynamoDB (NoSQL)
A fast key-value/document database. You design around access patterns, not tables-with-joins. Stores users, saved crops, cached data.
Auth / Cognito / JWT
How a farmer logs in and the backend knows who they are. Cognito manages users; it issues a JWT (signed token) the app sends with each request.
Caching & staleness
Store weather/price data briefly so you don't hammer external APIs and it loads fast. Always show "last updated".
Cron / scheduled job (EventBridge)
Runs code on a timer — e.g. pull mandi prices every morning.
Rate limiting
Cap how often a client can call, so one user/bug can't overload it (and to respect free-tier API limits).

4 · Data & integrations (the app's fuel)

Third-party API
Someone else's data service you call. Weather → IMD / OpenWeather; prices → Agmarknet / e-NAM; soil → Soil Health Card.
API key & secrets
A password for an API. NEVER put it in frontend/GitHub — store in AWS Secrets Manager, use from the backend only.
Geocoding / lat-long
Turning "Bhupalpally" into coordinates that weather APIs need.
Data pipeline / ETL
Fetch → clean → store external data on a schedule so the app reads *your* fast, reliable copy.
Rule-based engine
The crop-recommendation "brain" for v1: explicit if season/soil/rainfall then crops[] rules. Explainable + trustworthy + no ML data needed.

5 · Quality, DevOps & shipping

Git / branch / PR
Version control. You + brother work on branches, open Pull Requests, review each other before merging to main.
CI/CD (GitHub Actions)
On every push: automatically run tests/lint (CI) and deploy (CD). Keeps main always working.
Testing: unit / integration / e2e
Unit = one function; integration = pieces together (API+DB); e2e = whole flow like a user. Ship with tests, not "it worked once".
Linting / formatting / types
ruff+mypy (Python), ESLint+TypeScript (web). Catches mistakes + keeps code consistent across two people.
Infrastructure as Code (AWS CDK)
Your cloud setup written as code, versioned + repeatable. No clicking in the AWS console.
Environments (dev / prod)
A safe sandbox vs the real thing farmers use. Never test on prod.
Observability (logs / metrics / alarms)
CloudWatch logs + alarms so you know when something breaks in the pilot.

6 · Product & UX

Wireframe → Prototype → MVP
Sketch → clickable fake-data mockup (what you have now) → smallest real version that helps one farmer.
Accessibility & literacy-first
Big tap targets, icons, minimal text, high contrast, maybe voice. Assume low literacy + Telugu.
Low-bandwidth design
Small payloads, cache aggressively, degrade gracefully offline.

7 · Domain terms (agriculture / Telangana)

Kharif / Rabi
India's two main cropping seasons — Kharif (monsoon, ~Jun–Oct), Rabi (winter, ~Nov–Mar). Recommendations are season-specific.
Mandi & quintal
Mandi = govt-regulated wholesale market where crops sell. Quintal = 100 kg; prices quoted ₹/quintal.
Agmarknet / e-NAM
Govt platforms publishing daily mandi prices — our market-data source.
IMD
India Meteorological Department — official weather + forecasts.
Soil Health Card
Govt scheme with a farmer's soil nutrient data — feeds crop + fertilizer advice.
Black (regur) soil
Common in Telangana; good for cotton, paddy, gram — factors into recommendations.

Learn-by-reverse-engineering path: build the prototype's Weather screen for real first (fetch → cache → display) — it touches API keys, caching, TS types, and a React component end to end. Master that one slice, the rest rhymes.
